# 02. 검증 지표 및 검증 계획

> ZONE-2의 3대 핵심 기능이 실제 환경에서 작동하는지 **3단계로 검증**한다. 검증 지표는 기능당 1개씩 총 **5개**. 각 단계 기준 미달 시 보완 후 다음 단계로 진행.
> 검증 결과는 **중간보고회(8월)** 와 **결과보고서(11월)** 에 정량 데이터로 포함하여 재단에 제출한다.

---

## 5대 검증 지표

| # | 대상 | 검증 지표 | 목표 | 측정 방법 | 검증 시점 |
|---|------|-----------|------|-----------|-----------|
| 1 | 크로스뷰 매칭 엔진 | 매칭 정확도 (Precision@5) | **≥ 70%** | 수동 태깅 정답셋 50쌍 대비 상위 5건 일치율 | 1단계 (7월) |
| 2 | AI 팟캐스트 | 정상 발행률 — 요구 기준(주3회×4주 = 12건/월) 대비 실제 공개 편수 | **≥ 100%** (운영은 매일 발행 → 초과 달성으로 표기, 2026-10-25) | 관리자 대시보드 발행/승인 로그 | 2단계 (9월) |
| 3 | 공론 온도계 | 15분 갱신 정상 작동률 | **≥ 95%** | 서버 모니터링 로그 (Cloudflare Cron 실행 로그) | 2단계 (9월) |
| 4 | 서비스 전체 | 베타 참여자 재방문율 | **≥ 30%** | GA4 / Cloudflare Web Analytics 재방문 분석 (옥천 독자 50명, 2주) | 3단계 (10월) |
| 5 | 운영 체계 | 운영자 검수 승인율 | **≥ 85%** | 승인/반려 로그 (관리자 대시보드) | 3단계 (10월) |

> 지표는 **기능 결과(정확도·발행률·작동률·재방문·승인율)** 로 측정하며, 실 구현 스택(Claude/Supabase/Cloudflare) 기준으로 동일하게 검증한다.

---

## 3단계 검증 계획

### 1단계 — 단위 검증 (7월, 1단계 개발 완료)
**검증 내용**
- 양사 CMS 데이터 수집 파이프라인 정상 작동 확인
- 크로스뷰 매칭 엔진: 최근 3개월 기사 대상, 수동 태깅 50쌍으로 정확도 측정
- YouTube Data API + 옥천신문 CMS API 연동 안정성

**통과 기준**
- 매칭 정확도 **≥ 70%**
- API 수집 성공률 **≥ 95%**

---

### 2단계 — 통합 검증 (9월, 2단계 개발 완료)
**검증 내용**
- AI 팟캐스트: 데이터 수집 → 스크립트 생성 → TTS → 오디오 전 과정 E2E, **주 3회 × 4주 연속** 발행 테스트
- 공론 온도계: 15분 단위 자동 갱신 4주 연속 작동 확인
- 크로스뷰 + 온도계 + 팟캐스트 **3기능 연동** 테스트

**통과 기준**
- 팟캐스트 정상 발행률 **100% (12건/월)**
- 온도계 갱신률 **≥ 95%**

---

### 3단계 — 실사용 검증 / Beta (10/1~10/20, 2주간)
**검증 내용**
- 옥천신문 구독자 **50명 초청**, 2주간 실사용 파일럿
- 크로스뷰 소비 패턴 + 팟캐스트 청취율 로그 수집
- 운영자(MBC충북+옥천신문) 검수 워크플로 실전 운영
- 이용자 만족도 설문 (10점 척도)

**통과 기준**
- 재방문율 **≥ 30%**
- 운영자 승인율 **≥ 85%**

## 검증 미달 시 대응 (Fallback)

| 미달 시나리오 | 예상 원인 | 대응 |
|--------------|-----------|------|
| 매칭 정확도 < 70% | 양사 기사 표현 차이가 큼 (같은 이슈, 다른 키워드) | 시맨틱 유사도(임베딩) 가중치 상향 + 수동 매칭 룰 10건 추가 |
| 팟캐스트 발행 누락 | Claude API 응답 지연 / TTS 변환 실패 | API 타임아웃 3→5분 확대 + TTS 백업 서비스(CLOVA) 전환 루틴 |
| 재방문율 < 30% | 초기 콘텐츠 양 부족 / 알림 미설정 이탈 | 카카오톡 알림 구독 유도 강화 + 옥천신문 지면 QR코드 노출 |

## 측정 인프라

| 측정 항목 | 도구 | 비고 |
|-----------|------|------|
| 매칭 정확도 | 정답셋 시드 + 평가 스크립트 (`scripts/report/eval-matching.ts` → `lib/metrics/matching`) | 1단계 |
| 팟캐스트 발행/승인 로그 | `podcast_episodes` 테이블 status 추적(날짜별 published 유무) | 2단계 |
| 온도계 갱신 작동률 | launchd 15분 크론 + `temperature_runs` 테이블(`stats` 에 매칭·분류 건수) | 2단계 |
| 재방문율 | **자체 익명 방문 기록 `site_visits`**(2026-10-11 배포부터, #181) — CF Web Analytics 는 재방문 지표가 없어 대체. 시범단 기간은 측정 수단 미가동으로 소명 | 3단계 |
| 오늘·누적 방문(공개) | 푸터 한 줄 + 관리자 대시보드(2026-10-26 대표 지시). **오늘** = 오늘(KST) 순방문자, **누적** = `site_visits_daily` 일별 순방문자 합(0029, 영구) — `site_visits` 는 180일 뒤 지워지므로 "중복 없는 누적"은 유지할 수 없어 일별 합으로 정의(대표 결정). 같은 사람이 이틀 오면 누적 2 | 10/26~ |
| 검수 승인율 | `moderation_logs` 테이블 (approve+edit_approve / reject). confirm(한쪽 확인)·auto_publish(팟캐 마감 공개, #185)·cleanup(운영 정리 — 중복 페어 통합·클립 제외, #189) 은 분자·분모 모두 제외. **측정 시작일 2026-09-24**(시범단 시작 = 운영자 검수 시작, `APPROVAL_MEASURE_START`) — 7~9월 중순의 승인·반려 로그는 개발 중 검수 화면 점검이라 어떤 구간에서도 뺀다(대표 2026-10-27). 대시보드 기본 구간은 10월(10/1~오늘), "전체 누적" 구간은 없음(대표 2026-10-29) | 3단계 |
| **대시보드** | 관리자 `/admin/metrics`(구간: 전체·시범단·최근 30일·**결과보고 2주 10/11~10/24**·**결과보고 누적 10/11~어제**(#190, 10/25), CSV) = `pnpm report:stage1` 과 같은 `lib/metrics` | 10/11~ |
